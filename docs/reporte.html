Panel IoT con Flet y un ESP32 simulado en Wokwi: control y monitoreo por MQTT y HTTP

Claudio Rafael Vasquez Lopez, 20192002377 · Axel David Cornejo Ortega, 20192030294
Eva Sarahí Membreño Argueta, 20232000863 · Brenda Nicole Santiago, 20212030857
Daniel Orlando Fuentes Teruel, 20212020451 · José Omar Baca Aguilar, 20172030218

Universidad Nacional Autónoma de Honduras, Paradigmas de Programación

Resumen—Se presenta una aplicación en Python con el marco Flet que controla un microcontrolador ESP32 simulado en Wokwi y muestra en tiempo real las lecturas de sus sensores. Cada elemento de un formulario de ejemplo se asoció a una acción física: encender un LED, mover un servomotor, fijar el color de un LED RGB y de un anillo de LEDs, escribir en una pantalla OLED y activar un zumbador. El firmware en MicroPython atiende de forma concurrente un servidor web propio y un cliente de publicación y suscripción con el mismo formato de mensajes. Como el simulador gratuito sólo admite conexiones salientes, la vía viable sin costo fue un intermediario público de mensajería. Las pruebas sobre el simulador confirmaron todos los controles y lecturas, con tiempos de 0,6 s hacia el simulador y 1,1 s en sentido inverso.

Palabras clave— Internet de las cosas, MicroPython, interfaces gráficas de usuario.

I. Introducción

Las interfaces que controlan dispositivos físicos combinan tres paradigmas del curso: la programación orientada a eventos, que gobierna la interfaz; la orientada a objetos, que organiza los componentes; y la concurrente, que atiende la red y el hardware a la vez. Este trabajo los aplica en una aplicación Flet [1] que se comunica con un ESP32 programado en MicroPython [2] y simulado en Wokwi [3].

Se partió de un fragmento que conecta el ESP32 a la red Wokwi-GUEST y consulta una API con urequests. El objetivo fue que el ESP32 actuara como servidor web y que la aplicación encendiera un LED, enviara el valor de un control deslizante y mostrara en un cuadro de texto la información recibida. El código fuente está disponible en [9].

B. Arquitectura de comunicación

En el simulador web el ESP32 sólo puede abrir conexiones salientes; para alcanzar un servidor en el ESP32 desde la computadora se requiere la pasarela privada de Wokwi, disponible en planes de pago [3], [5]. Por eso el firmware ofrece dos transportes con los mismos mensajes JSON (Fig. 1): MQTT [4], donde el ESP32 y la aplicación se conectan a un intermediario público [6] mediante umqtt.simple y paho-mqtt [8]; y HTTP directo, donde el ESP32 es el servidor en el puerto 80.

C. Protocolo y firmware

Un comando contiene sólo los campos modificados y un estado reúne sensores, salidas, colores del anillo y eventos recientes (Apéndice A). Cada evento lleva un identificador creciente; así la aplicación no repite eventos y detecta un reinicio del ESP32. Por MQTT se usan tres temas bajo unah/paradigmas/<código>: estado, control y conexion, este último con una última voluntad offline y un intervalo de mantenimiento de 15 s.

El firmware ejecuta tareas cooperativas de asyncio en un solo núcleo: servidor HTTP, cliente MQTT, sensores cada 2 s, anillo cada 80 ms y pantalla cada 250 ms. Cada comando se valida: los números se limitan a su rango, se rechazan valores desconocidos y un JSON inválido no detiene el programa. Una temperatura superior a 35 °C genera una alerta.

E. Paradigmas aplicados

La clase Conexion concentra la cola de cambios y el filtrado de eventos; ConexionMQTT y ConexionHTTP sólo redefinen sincronizar, y la interfaz usa cualquiera sin distinguirlas (polimorfismo). Cada control registra un manejador de eventos; en el firmware, el pulsador usa una interrupción. Como Flet ejecuta los manejadores en otros hilos, la cola se protege con un cerrojo y conserva sólo el último valor de cada campo, de modo que arrastrar el deslizante no satura al ESP32.

F. Verificación

Se usaron tres niveles: doce pruebas automáticas con pytest; el firmware ejecutado sin cambios en la computadora con módulos de MicroPython imitados; y pruebas de extremo a extremo en el navegador con Wokwi y el intermediario broker.hivemq.com.

IV. Discusión

El firmware cumple el planteamiento de servidor web, pero en el simulador gratuito ese servidor no es accesible. MQTT resolvió la restricción al invertir el sentido de las conexiones, a costa de que el servidor pase a ser el intermediario y de una latencia mayor, que en las pruebas permitió operar el LED y el servomotor de forma interactiva. Un Mosquitto propio expuesto con ngrok funcionó en local, pero el túnel TCP gratuito exige registrar una tarjeta y cambia de dirección [7]. El intermediario público permite que cualquiera que conozca el tema lea o envíe mensajes; un código propio lo mitiga sin eliminarlo.

V. Conclusiones

Se desarrolló una aplicación Flet que controla y monitorea un ESP32 en Wokwi, con todas las funciones verificadas de extremo a extremo. Separar la interfaz de la capa de conexión y usar un protocolo único para HTTP y MQTT permitió adaptarse a la restricción del simulador sin rehacer la interfaz. Como trabajo futuro se propone un intermediario privado con TLS y la prueba en una placa física.

Apéndice B. Ejecución

  1. En Wokwi, crear un proyecto ESP32 con MicroPython y pegar wokwi/main.py y wokwi/diagram.json del repositorio [9].
  2. Ejecutar uv run flet run y conectar por MQTT a broker.hivemq.com:1883 con el mismo código del firmware.
  3. Sin Wokwi: uv run python tools/esp32_en_pc.py. Pruebas: uv run pytest.
